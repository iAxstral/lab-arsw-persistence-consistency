# ADR-001 · Persistencia y garantías del tablero

- **Equipo / integrantes:** ARSW-EQP-06 · Tomás Olaya Díaz · Isaac David Burgos Cervantes · Javier Romero
- **Estado:** aceptado
- **Fecha y commit:** 2026-10-31 · código de la solución en `719d3b6` (`services/content/decisions.py`); evidencia y documentación en el commit final de `main`

## Contexto

Un tablero colaborativo con dos servicios de negocio:

- **Gestión** (PostgreSQL): usuarios, tableros y membresías con `can_edit`. Es la **autoridad** de permisos.
- **Contenido y colaboración** (MongoDB + Redis): documento del tablero (título, versión, preferencias), caché de permisos y presencia.

Operaciones y datos críticos:

| Operación | Frecuencia | Qué no puede fallar |
|---|---|---|
| Leer tablero (`GET /boards/{id}`) | Muy alta (la carga k6 es 100 % lecturas) | Devolver un documento válido con versión ≥ 1 |
| Editar tablero (`PUT`) | Baja-media, concurrente entre pestañas/usuarios | **No perder ediciones** y **no aceptar escrituras de un usuario revocado** |
| Consultar permiso para la UI | Media | Puede estar desactualizado ≤ 60 s |
| Heartbeat de presencia | Alta y periódica | Nada crítico: aproximada, efímera (20 s) |

Defectos medidos en la base (`entrega/evidencias/json/antes-baseline-20261031T122427Z.json`):

1. Dos PUT con `expected_version=1` → **200 y 200**, versión final 3, se pierde el cambio de Ana (edición perdida).
2. Luis revocado en PostgreSQL pero con permiso en caché → **200**, el documento cambió a «Cambio prohibido».
3. Presencia sin TTL: 22 s después seguía `users:["ana"]`.
4. Con Redis detenido el heartbeat respondía **503**; con Gestión detenida y caché primada la escritura respondía **200** (`antes-redis-down-*.json`, `antes-authority-down-*.json`).

Restricciones: instancias únicas (sin réplicas, sin consenso, sin CAP), sin transacciones distribuidas entre Gestión y Contenido, identidades simuladas por header, 150 minutos.

## Decisión

### 1. Motores (se mantiene la distribución inicial)

- **PostgreSQL** para membresías/permisos: integridad referencial (FK), unicidad por `(board_id, user_id)` (PK) y transacciones con `ROLLBACK`. Es la fuente autoritativa.
- **MongoDB** para el documento del tablero, con **preferencias embebidas** (pequeñas, acotadas, siempre se leen juntas).
- **Redis** solo para datos **efímeros o derivados**: presencia (TTL 20 s) y caché de permisos para la UI (TTL 60 s). Redis es **opcional**.

Detalle por dato en [`MATRIZ.md`](MATRIZ.md).

### 2. Frontera de atomicidad: el documento del tablero (TODO 1)

```python
collection.find_one_and_update(
    {'_id': board_id, 'version': expected_version},       # condición
    {'$set': {'title': title}, '$inc': {'version': 1}},  # efecto
    return_document=ReturnDocument.AFTER)
```

Condición y efecto se evalúan en **una única operación atómica sobre un documento**. Si dos clientes envían la misma versión, solo uno coincide con el filtro; el otro recibe `None` → **409 Conflict** («recargue antes de editar»). No se usa `find` + `update` porque entre ambos otro escritor podría cambiar el documento. Un 409 es un **rechazo de negocio correcto**, no una falla técnica: protege el cambio de quien llegó primero.

### 3. Política de caché y garantía de escritura (TODO 2)

```python
return authoritative_permission(user, board_id) is True
```

- La **caché** (Redis, 60 s) se usa solo para `GET /permissions` (pintar la UI). Una concesión cacheada no demuestra que siga vigente.
- Toda **escritura** consulta a Gestión/PostgreSQL. Garantía: **una escritura que comienza después de que la revocación fue confirmada se rechaza con 403** y el documento queda intacto.
- **Fail-closed:** si Gestión no responde, `authoritative_permission` lanza `HTTPException(503)` y la dejamos propagar. Nunca se convierte una falla de validación en un permiso concedido. `is True` además rechaza cualquier respuesta que no sea un booleano verdadero.
- No basta acortar el TTL (solo achica la ventana, no la elimina) ni ocultar el botón (el cliente puede llamar a la API directamente).

Elegimos el callback autoritativo frente al cacheado sabiendo su **costo**: una llamada HTTP extra a Gestión por escritura (el P95 de Gestión observado en Grafana ronda 24 ms, que se suma a la edición) y que la edición depende de la disponibilidad de Gestión. Se acepta porque editar es mucho menos frecuente que leer, y un permiso revocado que sigue funcionando es un problema de seguridad.

### 4. Presencia efímera y degradación (TODO 3)

```python
try:
    return bool(client.set(key, 'online', ex=ttl))
except RedisError:
    return False
```

- `SET key online EX 20`: valor y expiración en **una sola escritura**; cada heartbeat la renueva (evidencia: TTL 20 → 15 → heartbeat → 20 en `logs/10-presencia-ttl.txt`).
- Si Redis no responde se retorna `False`: la API responde **200 con `available:false`** y aumenta `lab_degraded_total{feature="presence"}`. Solo se captura `RedisError`; un error de programación seguiría siendo visible como 500.
- No se reporta presencia disponible cuando no se pudo registrar.

### 5. Degradación: qué sigue y qué se detiene

| Dependencia caída | Lectura del tablero | Edición | Permiso para UI | Presencia |
|---|---|---|---|---|
| **Redis** | ✅ 200 | ✅ 200 (autoridad = Gestión) | ✅ 200 (fallback a Gestión) | ⚠️ 200 `available:false` (degradada) |
| **Gestión / PostgreSQL** | ✅ 200 | ⛔ **503** deliberado (no se puede validar) | ⚠️ puede responder desde caché (solo UI) | ✅ |
| **MongoDB** | ⛔ 503 | ⛔ 503 (no hay dónde escribir) | ✅ | ✅ |

## Alternativa considerada

**A. PostgreSQL + JSONB para el contenido (un solo motor transaccional para permisos y documento).**
`UPDATE boards SET doc = …, version = version + 1 WHERE id = $1 AND version = $2` junto con `SELECT can_edit FROM memberships … FOR SHARE` en la **misma transacción**. Ventaja: cerraría la ventana validar→escribir (una revocación concurrente esperaría al lock o vería el commit). **Descartada** en esta práctica porque obliga a fusionar las fronteras de Gestión y Contenido (o a compartir base entre servicios), migrar datos en clase y perder la flexibilidad del documento; el laboratorio exige la garantía para revocaciones *confirmadas antes* de la escritura, que ya cumplimos.

**B. Eliminar Redis.** Presencia en memoria del proceso y sin caché de permisos. Más simple y una dependencia menos, pero la presencia no funcionaría con más de una réplica de Contenido y cada carga de la UI iría a Gestión. **Descartada**: Redis aporta TTL nativo y, gracias a la degradación, su caída no afecta la edición.

**C. Autorizar con la caché y acortar TTL a 1–5 s.** Menos carga sobre Gestión, pero sigue existiendo una ventana en la que un usuario revocado escribe, y si Gestión cae se seguiría concediendo con datos viejos. **Descartada** por el contrato de 403/503.

## Consecuencias

**Positivas**
- Sin ediciones perdidas: exactamente un 200 y un 409 ante la misma versión; la versión aumenta una sola vez.
- Revocación confirmada → 403 inmediato aunque la caché diga `can_edit:true` con TTL 60 (`logs/09-revocacion-vs-cache.txt`).
- Redis deja de ser punto único de falla para la edición.

**Costos**
- Cada escritura hace una llamada síncrona a Gestión (latencia y acoplamiento temporal).
- Más 409 visibles para los usuarios bajo edición concurrente: es el precio de no perder cambios; la UI debe pedir recargar y reintentar.
- La UI puede mostrar «puede editar» hasta 60 s después de una revocación (la escritura igualmente se rechaza). Mejora futura: invalidar `permission:*` con un evento de Gestión.

**Fallas toleradas:** Redis caído (presencia degradada, caché omitida). **Fallas que bloquean (deliberadamente):** Gestión/PostgreSQL caído bloquea escrituras con 503 (preferimos no disponibilidad a una escritura no autorizada); MongoDB caído bloquea lectura y escritura del contenido.

**Ventana entre validar permisos y escribir (límite conocido).** Gestión y Contenido no comparten transacción. Secuencia problemática:

```
t0  Contenido consulta a Gestión → can_edit = true
t1  Admin revoca a Luis en PostgreSQL (commit)
t2  Contenido ejecuta find_one_and_update en MongoDB → se guarda
```

La escritura de t2 se acepta aunque la revocación terminó antes del guardado. Nuestra garantía cubre solo revocaciones **confirmadas antes de iniciar** la escritura. Opciones para cerrarla: (a) una sola base/transacción (alternativa A); (b) **época/versión de permisos**: Gestión incrementa `perm_version` en cada revocación y Contenido guarda `{… perm_version}` con un CAS que se revalida después de escribir, revirtiendo o marcando la edición si cambió; (c) tokens de autorización de vida muy corta firmados por Gestión con revocación por lista; (d) aceptar la ventana (milisegundos) y auditarla en el historial.

## Historial creciente

- **Almacenamiento:** colección separada `board_history` en MongoDB (o tabla `board_history` en PostgreSQL), una entrada **append-only** por versión: `{board_id, version, title, preferences, author, at}`.
- **Índice:** único `{board_id: 1, version: -1}`; evita entradas duplicadas por versión y soporta el orden.
- **Consulta y paginación por cursor (keyset):** primera página `find({board_id}).sort({version:-1}).limit(20)`; siguientes `find({board_id, version: {$lt: ultimaVersionVista}})…limit(20)`. Evita `skip`, que se degrada con páginas profundas.
- **Escritura:** tras un CAS exitoso, insertar la entrada con la versión resultante; si falla, reintento idempotente gracias al índice único. Con replica set, ambas en una transacción multi-documento.
- **Retención:** política explícita (p. ej. 90 días o últimas N versiones) con archivado.
- **Por qué no embeberlo ilimitado:** el documento crecería sin cota (límite 16 MB de MongoDB), cada `GET` del tablero (la operación más frecuente) transferiría todo el historial, cada edición reescribiría un documento cada vez más grande y la contención (409) aumentaría; tampoco se podría paginar eficientemente.

## Evidencia

Todo en [`EVIDENCIAS.md`](EVIDENCIAS.md); resumen:

| Prueba | Antes | Después |
|---|---|---|
| `acceptance` / `baseline` | 3 de 4 `passed:false` | **4/4 `passed:true`, exit 0** (4 ejecuciones) |
| Ediciones concurrentes | `[200, 200]`, v1→v3 | `[200, 409]`, v1→v2 |
| Permiso revocado | 200, documento cambiado | **403**, documento intacto |
| Presencia 22 s | sigue `ana` | expiró (`users:[]`) |
| `redis-down` | presencia **503** | edición 200 + presencia **200 `available:false`** |
| `authority-down` | **200** con caché | **503** |
| k6 carga (5 VU, 100 s) | P95 7,35 ms, 0 % fallos | P95 7,92 ms, 0 % fallos |

Dashboard exportado: [`dashboard.json`](dashboard.json) (10 paneles) y capturas en `evidencias/capturas/grafana-*.png` con la ventana horaria UTC visible.

**Lo que las pruebas NO demuestran:**
- No cubren la carrera revocación-después-de-validar (descrita arriba); ninguna prueba la ejercita.
- k6 solo hace lecturas: no mide el costo de la llamada a la autoridad bajo **escrituras** concurrentes ni la tasa de 409 bajo carga real.
- Instancias únicas en un solo host: no hay replicación, particiones de red ni CAP; detener Redis es una falla de dependencia, no una partición.
- `lab_dependency_up` mide conectividad cada 5 s, no la corrección de las respuestas; `up=1` solo prueba que Prometheus pudo leer métricas.
- Los umbrales de k6 (P95 < 500 ms) se cumplieron con mucha holgura en esta máquina; no es una medición de capacidad.
